# 修复核验全链路 — 缓存一致性与设备分配技术设计 v1.0

 > **范围**：R11~R14（后端缓存基础设施、preDispatch/dispatch 接口增强、分布式锁、幂等控制）  
 > **对应 PRD**：`修复核验全链路-vul-pass-PRD.md` v2.0.0 §5.2 / §5.2.1 / §5.3.1  
 > **对应开发计划**：`修复核验全链路-开发计划-v3.0.md` R11~R16  
 > **日期**：2026-07-21  
 > **状态**：待评审

 ---

 ## 1. 背景与目标

 ### 1.1 背景

 当前 `preDispatch` 仅返回建议设备，`dispatch` 阶段可能因设备状态变化导致实际落库子任务与预览不一致。为实现 PRD 要求的"预览子任务与实际产生子任务完全一致"，必须引入 preview plan 缓存机制。

 ### 1.2 目标

 1. `preDispatch` 生成的 plan 在 30 分钟内可被 `dispatch` 原子消费。
 2. 用户可在预览页为每个子任务指定安全资源设备，选择只存在前端，dispatch 时回传。
 3. 后端校验用户选择：`engHash` 必须在对应 group 的 `candidateEngHashes` 中。
 4. 防止重复提交、并发提交、跨会话共享。
 5. Redis 异常时拒绝 dispatch，不允许降级重新生成 plan。

 ### 1.3 当前实现问题

 当前 `VerifyFixConfirmTokenStore` 使用 **JVM 内存 Map** 存储 `VerifyFixDispatchPlan`，存在以下问题：

 1. **多实例不共享**：微服务多节点部署时，preview 与 dispatch 可能落到不同节点，token 失效。
 2. **重启丢失**：应用重启后所有预览 plan 丢失。
 3. **数据不完整**：只缓存了 `VerifyFixDispatchPlan`，未缓存 preview 时加载的**工单上下文、资产列表、系统漏洞实例列表**等关键原始数据。dispatch 阶段重新查询这些数据，可能因状态变化导致不一致。

 因此，必须将存储迁移到 **Redis**，并扩展缓存内容以包含完整的 preview 上下文。

 ## 2. 总体设计原则

 | 原则 | 说明 |
 |------|------|
 | 一份 plan 一个 token | `confirmToken` 是 plan 的唯一句柄 |
 | token 强归属 | 与 `userId + sessionId + tenantId + orderId` 绑定 |
 | 前端只改设备 | 不实时写缓存；最终选择 dispatch 时回传 |
 | 后端原子消费 | 查-验-写-删在一个 Lua 脚本或 Redis 事务内完成 |
 | 成功即销毁 | dispatch 成功后立即删除 plan key |
 | 强一致优先 | Redis 不可用则拒绝 dispatch |

 ---

 ## 3. 关键概念与术语

 | 术语 | 说明 |
 |------|------|
 | `confirmToken` | 签名 token，包含归属信息，30 分钟有效 |
 | `groupKey` | 物理子任务唯一标识：`{wave}_{strategyClass}_{procMethod}_{batchIndex}_{seq}` |
 | `candidateEngHashes` | 某子任务可选的安全资源设备列表 |
 | `groupEngHashAssignments` | dispatch 时前端回传的 `{groupKey: engHash}` 映射 |
 | `CachedPlan` | Redis 中缓存的 plan 对象 |

 ### 5.2 confirmToken 签名机制

 #### 5.2.1 Token 内容

 ```text
 payload = userId + ":" + sessionId + ":" + tenantId + ":" + orderId + ":" + timestamp + ":" + nonce
 confirmToken = HMAC-SHA256(payload, serverSecret)
 ```

 实际实现建议：使用 JWT 或自定义序列化 + HMAC。token 本身需可解析，以便先验后查 Redis。

 #### 5.2.2 解析与校验

 ```java
 public class ConfirmTokenSigner {
     public String sign(Owner owner);
     public TokenPayload verify(String token);
 }
 ```

 - 签名失败：拒绝
 - token 过期（timestamp + 30min < now）：拒绝
 - payload 被篡改：拒绝

 ### 5.4 preDispatch 改造

 #### 5.4.1 调用链

 ```text
 VulScanTaskUi.preDispatch()
   → VulScanTaskAppServiceImpl.preDispatch()
     → VerifyFixDispatchPlanner.plan()
     → EngDeviceMatcher.match() // 生成 candidateEngHashes
     → DispatchPlanAssembler.assemble()
     → VerifyFixPlanCacheRepository.saveIfAbsent()
 ```

 #### 5.4.2 关键改动点

 1. `preDispatch` 阶段需加载并保留完整的 preview 上下文：
    - `orderContext`：从 `commandEvent.getVulCommonParams(orderId)` 获取的工单关键字段。
    - `assetList`：前端传入或从 `assetInfoRange` 解析的完整资产列表。
    - `vulInstList`：修复核验时从 `vulInfoRange` / `vulInfoStat` 加载的系统漏洞实例列表。
    - `forcedEngHashes`：跨级联动时从 `eng_hash_cnt` 解析的强制设备池。
    - `userParams`：前端传入的任务参数（`tskType`、`tskModel`、`tskAction`、`tskPhase`、`procMethod`、`source`、`reportType`、`matchAssetRule`、`autoSubmit`、`syncAssetPort`、`primaryEngHash`、`crossEngHash`）。
 2. `VerifyFixDispatchPlanner` 生成每个 group 时，同时生成 `candidateEngHashes` 和 `defaultEngHash`。
 3. `DispatchPlanAssembler` 把 candidate 列表映射到前端 DTO。
 4. `VulScanTaskAppServiceImpl.preDispatch()` 生成 `confirmToken`，组装 `CachedPlan`（含 `previewContext` + `plan`），调用 `saveIfAbsent()` 写 Redis。
 5. 原 `VerifyFixConfirmTokenStore`（JVM Map）**废弃**，统一使用 Redis 实现。

 ### 5.5 dispatch 改造

 #### 5.5.1 调用链

 ```text
 VulScanTaskUi.dispatch()
   → VulScanTaskAppServiceImpl.dispatch()
     → VerifyFixPlanCacheService.getAndValidate() // 从 Redis 取 CachedPlan
     → VerifyFixDeviceAssignmentValidator.validate() // 校验设备分配
     → VulScanTaskAppServiceImpl.buildTaskFromCachedPlan() // 用缓存上下文构建 VulScanTaskDO
     → VulScanTaskSubDomainServiceImpl.dispatch()
     → VerifyFixPlanCacheRepository.consume() // 原子删除 plan
 ```

 #### 5.5.2 关键校验

 ```java
 public class VerifyFixDeviceAssignmentValidator {
     public void validate(CachedPlan cachedPlan, Map<String, String> assignments) {
         for (CachedSubTask subTask : cachedPlan.getPlan().getSubTasks()) {
             String assigned = assignments.getOrDefault(
                 subTask.getGroupKey(),
                 subTask.getDefaultEngHash()
             );

             Assert.notBlank(assigned, "子任务 %s 未分配设备", subTask.getGroupKey());
             Assert.isTrue(
                 subTask.getCandidateEngHashes().contains(assigned),
                 "子任务 %s 分配的设备 %s 不在候选池中",
                 subTask.getGroupKey(), assigned
             );

             // 校验 engType bit（候选池已过滤，此处二次兜底）
             EngInfo engInfo = engInfoRepository.findByHash(assigned);
             Assert.isTrue(
                 (engInfo.getEngType() & subTask.getRequiredEngTypeBit()) != 0,
                 "子任务 %s 设备 engType 不匹配", subTask.getGroupKey()
             );
         }
     }
 }
 ```

 #### 5.5.3 从缓存构建任务

 `VulScanTaskAppServiceImpl.dispatch()` 不再重新调用 `loadOrder()` / `loadEngHash()` / `initParams()` 从数据库/工单加载数据，而是从 `CachedPlan.previewContext` 构建 `VulScanTaskDO`：

 ```java
 private VulScanTaskDO buildTaskFromCachedPlan(
         CachedPlan cachedPlan,
         VulTaskDispatchDTO params,
         Map<String, String> assignments) {

     VulScanTaskDO task = new VulScanTaskDO();
     PreviewContext ctx = cachedPlan.getPreviewContext();

     // 1. 基础参数：以缓存中的 userParams 为准，dispatch 入参做一致性校验
     UserParams up = ctx.getUserParams();
     task.setTskType(up.getTskType());
     task.setTskModel(up.getTskModel());
     task.setTskAction(up.getTskAction());
     task.setTskPhase(String.valueOf(up.getTskPhase()));
     task.setProcMethod(up.getProcMethod());
     task.setReportType(up.getReportType());
     task.setMatchAssetRule(up.getMatchAssetRule());
     task.setAutoSubmit(up.isAutoSubmit());
     task.setSyncAssetPort(up.isSyncAssetPort());

     // 2. 工单上下文：直接取自缓存，不再查 commandEvent
     OrderContext oc = ctx.getOrderContext();
     task.setOrderId(oc.getOrderId());
     task.setOrderType(oc.getOrderType());
     task.setOrderSubType(oc.getOrderSubType());
     task.setCtxCode(oc.getCtxCode());
     task.setAssetInfoRange(oc.getAssetInfoRange());
     task.setVulKeys(oc.getVulKeys());
     task.setVulInfoStat(oc.getVulInfoStat());
     task.setVulInfoId(oc.getVulInfoId());
     task.setSrcTktRole(oc.getSrcTktRole());
     task.setDstTktRole(oc.getDstTktRole());
     task.setSrcTktPrsn(oc.getSrcTktPrsn());
     task.setDstTktPrsn(oc.getDstTktPrsn());
     task.setAssetOwnerInfo(oc.getAssetOwnerInfo());
     task.setPwDictRange(oc.getPwDictRange());
     task.setAstUnitNum(oc.getAstUnitNum());

     // 3. 资产与实例：直接取自缓存
     task.setAssetList(ctx.getAssetList());
     task.setVulInstList(ctx.getVulInstList());
     task.setVulInstNum(CollUtil.size(ctx.getVulInstList()));

     // 4. 修复核验 plan：应用用户设备分配
     VerifyFixDispatchPlan plan = cachedPlan.getPlan();
     applyUserDeviceAssignments(plan, assignments);
     task.setVerifyFixPlan(plan);
     task.setConfirmToken(params.getConfirmToken());

     // 5. 运行时字段
     task.setTskProgress(1);
     task.setTskStat(MainTaskStatEnum.PENDING_START.getCode());
     task.setTskStartTime(new Date());
     task.setOrderAct(0);

     return task;
 }
 ```

 **一致性校验**：
 - `params.getOrderId()` 必须与 `cachedPlan.owner.orderId` 一致。
 - `params.getTskPhase()` 必须与 `cachedPlan.previewContext.userParams.tskPhase` 一致。
 - 不一致时拒绝 dispatch，提示"预览参数与下发参数不一致，请重新预览"。

 ### 5.6 原子消费脚本

 ```lua
 -- consume_plan.lua
 -- KEYS[1] = verify-fix:plan:{confirmToken}
 -- KEYS[2] = verify-fix:dispatched:{confirmToken}

 if redis.call('exists', KEYS[1]) == 0 then
     return 0
 end

 redis.call('setex', KEYS[2], 604800, '1')
 redis.call('del', KEYS[1])
 return 1
 ```

 Java 调用：

 ```java
 @Override
 public boolean consume(String confirmToken) {
     String planKey = keyOfPlan(confirmToken);
     String dispatchedKey = keyOfDispatched(confirmToken);
     DefaultRedisScript<Long> script = new DefaultRedisScript<>(CONSUME_LUA, Long.class);
     Long result = redisTemplate.execute(script, Arrays.asList(planKey, dispatchedKey));
     return Long.valueOf(1L).equals(result);
 }
 ```

 ### 5.7 分布式锁实现

 ```java
 public class VerifyFixDispatchLock {
     private static final String LOCK_PREFIX = "verify-fix:lock:dispatch:";
     private static final Duration LOCK_TTL = Duration.ofSeconds(30);

     public boolean tryLock(String confirmToken) {
         String key = LOCK_PREFIX + confirmToken;
         return Boolean.TRUE.equals(
             redisTemplate.opsForValue().setIfAbsent(key, "1", LOCK_TTL)
         );
     }

     public void unlock(String confirmToken) {
         String key = LOCK_PREFIX + confirmToken;
         redisTemplate.delete(key);
     }
 }
 ```

 ### 5.8 幂等控制

 - 消费成功后写入 `verify-fix:dispatched:{confirmToken}`，TTL 7 天。
 - dispatch 前先判断幂等 key 是否存在，存在则直接拒绝。
 - 业务异常时幂等 key **不写入**，允许重试。
 - Redis 消费成功但业务落库失败（极端情况）：plan key 已删，幂等 key 已写。此时用户无法再次 dispatch，需重新 preview。

 ### 5.9 异常处理与降级策略

 | 异常 | 处理 |
 |------|------|
 | Redis 不可用 | 拒绝 dispatch，返回"系统繁忙，请重新预览" |
 | plan 不存在 | 返回"预览已过期，请重新预览" |
 | checksum 失败 | 返回"预览数据异常，请重新预览" |
 | owner 不匹配 | 返回"无权操作" |
 | token 已过期 | 返回"预览已过期，请重新预览" |
 | 幂等 key 已存在 | 返回"该预览计划已下发，请勿重复提交" |
 | 设备不在候选池 | 返回"子任务 X 分配设备不合法" |
 | 业务落库失败 | 记录失败次数，保留 plan，允许重试 3 次 |

 ### 5.10 缺失参数分析（对比原有 dispatch 方法）

 原有 `VulScanTaskAppServiceImpl.dispatch()` 通过以下步骤准备 `VulScanTaskDO`：

 ```text
 initTsk(params) → loadOrder(params, task) → loadEngHash(params, task) → initParams(task)
 ```

 其中 `loadOrder()` 从 `commandEvent.getVulCommonParams(orderId)` 重新查询工单，`initParams()` 从 `assetInfoRange` / `vulKeys` / `pwDictRange` 重新统计资产/漏洞/口令数量。修复核验流程在 `fillVerifyFixPlan()` 中还会重新加载 `VulArchiveInstDO` 实例列表。

 **这些重新查询会导致 preview 与 dispatch 之间的不一致**：

 | 数据 | 原方式 | 问题 | 新方式 |
 |------|--------|------|--------|
 | 工单上下文 | dispatch 时重新查 `commandEvent` | 工单字段可能在两次请求间被修改 | 缓存 `previewContext.orderContext` |
 | 排查资产列表 | dispatch 时从 `assetInfoRange` 重新查 | 资产范围可能变化 | 缓存 `previewContext.assetList` |
 | 系统漏洞实例 | dispatch 时重新加载 | 实例状态可能从 stat=5 变为其他，导致子任务不一致 | 缓存 `previewContext.vulInstList` |
 | 强制设备池 | dispatch 时重新解析 `eng_hash_cnt` | 设备池可能变化 | 缓存 `previewContext.forcedEngHashes` |
 | 用户选择的技术处置方式 | dispatch 时从 params 取 | 安全，但需与缓存校验一致 | 缓存 `previewContext.userParams.procMethod`，dispatch 入参校验 |
 | 任务模式 tskModel | dispatch 时从 params 取 | 安全 | 缓存 `previewContext.userParams.tskModel` |

 **结论**：`CachedPlan` 必须扩展 `previewContext`，保存 preview 阶段已确定的完整上下文数据。dispatch 阶段优先使用缓存数据构建 `VulScanTaskDO`，不再重新查询可能变化的数据源。

 ## 7. 边界条件与校验矩阵

 | 场景 | 期望行为 |
 |------|----------|
 | 用户两次点击预览 | 生成两个 confirmToken，各自独立 |
 | 用户 A 拿到用户 B 的 token | owner 校验失败，拒绝 |
 | 用户刷新页面 | 前端选择丢失，需重新预览（或 localStorage 暂存） |
 | 用户 30 分钟内未 dispatch | plan key TTL 过期，dispatch 失败 |
 | 用户快速双击确认下发 | 分布式锁 + 幂等 key 只让第一次成功 |
 | dispatch 业务失败 | plan 保留，失败次数 +1，允许重试 3 次 |
 | 3 次 dispatch 均失败 | plan key 删除，提示重新预览 |
 | Redis 在 dispatch 时挂了 | 拒绝 dispatch，不降级 |
 | 前端传了不存在的 groupKey | 校验失败，拒绝 |
 | 前端传了候选池外的 engHash | 校验失败，拒绝 |

 ---

 ## 8. 安全设计

 1. **Token 签名**：防止伪造和篡改。
 2. **Owner 双重校验**：token payload 校验 + value owner 校验。
 3. **候选池约束**：用户只能选后端给出的设备，不能任意指定。
 4. **分布式锁**：防止并发重复消费。
 5. **幂等标记**：防止网络重试导致重复下发。
 6. **Redis 异常拒绝**：不降级，避免不一致。

 ## 10. 依赖与风险

 ### 10.1 依赖

 - Redis 可用（已有，自动化处置演进已使用 Redis）
 - `VerifyFixDispatchPlanner` 已能生成 candidateEngHashes
 - `DispatchPlanAssembler` 已支持统一 dispatchPlan（Wave M）

 ### 10.2 风险

 | 风险 | 缓解 |
 |------|------|
 | Redis 单点故障导致 dispatch 不可用 | Redis 异常时拒绝 dispatch，用户重新预览即可 |
 | plan 数据过大 | 只存实例 ID，不存完整 DTO；必要时启用压缩 |
 | 消费成功但业务落库失败 | 幂等 key 已写，用户需重新 preview；可后续增加补偿通知 |
 | token 泄露 | token 含 sessionId 且 30 分钟过期；敏感操作需 owner 校验 |
