# 任务下发页面整改方案 v2.0（预览接口统一）

> 范围：`/vul-pass/vul-scan-task/pre/dispatch` 预览接口 + `asset-newleak-manage` 前端「任务下发」抽屉（系统漏洞工单 / 跨级联动 / 产品预警共用）
> 目标：把"阶段子任务链预览（phaseDispatchPreview）"与"修复核验子任务预览（verifyFixPlan）"两套并存、且在核验阶段互相矛盾的预览，**统一为按（工单类型 × 业务阶段）产出的单一子任务预分配结构 `dispatchPlan`**。
> 原则：YAGNI、最小 diff、改根因、零功能回归；复用已实现的 `VerifyFixDispatchPlanner` 分批与设备匹配能力，不重复造轮子。
> 前置：本方案是 v1.0 的演进。v1.0 已修复"选完设备仍报红无法下发"的 P0 死锁（SafeSourceDriver 未联动预览）。v2.0 解决更深层的架构问题：核验阶段两套预览同屏打架。

---

## 一、问题本质（v1.0 未触及的根）

`/pre/dispatch` 在**核验阶段（tskPhase=4）无条件返回两个并列字段**，二者对"要下发几条子任务、分几批、设备是否齐全"给出结构性矛盾的答案：

| 字段 | 数据源 | 分批口径 | 设备能力 | 核验阶段表现 |
|------|--------|---------|---------|-------------|
| `phaseDispatchPreview` | `PhaseDispatchPreviewBuilder` 阶段4**示意行** | 手动 `batchSize`（`AssetBatchSplitter.split`） | 仅单个 primary，无 eng_hash_cnt 池 | 🔴 全部"未匹配"、`canConfirm=false`、卡死确认按钮 |
| `verifyFixPlan` | `VerifyFixDispatchPlanner` | 自动 `AstUnitNum`（`shardByAstUnit` 按 IP 切） | Gate+Scan 波次、eng_hash_cnt 强制池、按修复状态筛 IP | ✅ 设备匹配、分批正确 |

### 三条代码级硬事实

1. **接口无条件返回双字段**：[VulScanTaskAppServiceImpl.java:552-558](project_backend/svmp/vul-pass/src/main/java/com/vtc/security/app/service/impl/VulScanTaskAppServiceImpl.java#L552) 先建 `verifyFixPlan`（仅阶段4），再**无条件**建 `phaseDispatchPreview`。方法注释自认"阶段4详细仍以 verifyFixPlan 为准"——明知次要却仍发出。
2. **分批权威在 verifyFixPlan**：[fillVerifyFixPlan:665](project_backend/svmp/vul-pass/src/main/java/com/vtc/security/app/service/impl/VulScanTaskAppServiceImpl.java#L665) 传入 `task.getAstUnitNum()` → `shardByAstUnit`（[:314-339](project_backend/svmp/vul-pass/src/main/java/com/vtc/security/domain/pass/service/verify/VerifyFixDispatchPlanner.java#L314)）按 IP 分组、每 AstUnitNum 个 IP 切一批；`<=0` 或 null 不切。即"AstUnitNum≠-1 时按其拆分，否则不分批"**已实现**。
3. **示意行错误夺取下发裁决权（真正 P0）**：阶段4 前端隐藏了 SafeSourceDriver → `engHashes` 为空 → primary=null → [PhaseDispatchPreviewBuilder.java:202-213](project_backend/svmp/vul-pass/src/main/java/com/vtc/security/domain/pass/service/dispatch/PhaseDispatchPreviewBuilder.java#L202) 示意行 `fillDevice` 标红"未匹配" → [:110-113](project_backend/svmp/vul-pass/src/main/java/com/vtc/security/domain/pass/service/dispatch/PhaseDispatchPreviewBuilder.java#L110) `canConfirm=false` → 前端 [AddTaskDrawer.vue:199](project_frontend/asset/asset-newleak-manage/src/views/VulnManagePlat/components/TaskSend/AddTaskDrawer.vue#L199) `!phasePreviewOk` 永久置灰，哪怕 verifyFixPlan 设备全匹配。

## 二、统一设计

### 2.1 出参归一为单一 `dispatchPlan`

`/pre/dispatch` 不再返回 `phaseDispatchPreview` + `verifyFixPlan` 两个并列字段，而是返回**单一 `dispatchPlan`**。以已成熟的 `VerifyFixDispatchPlan` groups 结构为骨架（它最接近"子任务预分配"语义），让阶段 0-3 也产出 groups。

```
dispatchPlan {
  phase, phaseName,
  orderType,                 // 工单/任务类型：sys / ganged / warn
  subTasks: [ {              // 统一子任务预分配（复用 VerifyFixPlanGroup 骨架 + 少量补字段）
    batchIndex, batchLabel,  // 分批：跨级联动=AstUnitNum 自动切；否则单批
    subTaskKind, subTaskTypeName, processOrder,
    procMethod, tskType, role,        // role：主扫/交叉厂家（验证阶段交叉扫描）
    engHash, engName, vendor, devIp, scannerSource,
    deviceRequired, deviceMatched,    // 设备规则裁决
    assetIps, instanceCount, uniqueIpCount,
    reportTypeHint, processHints,     // 展示辅助（来自原 phaseDispatchPreview row）
    warnings
  } ],
  summary { batchCount, subTaskCount, allDevicesMatched, dispatchMode, dispatchModeLabel },
  dualVendor,                // 仅验证阶段交叉扫描
  canConfirm, message,       // 单一裁决
  confirmToken               // 阶段4 需要；其他阶段可空
}
```

### 2.2 编排规则（按"工单类型 × 阶段"填充 subTasks）

| 阶段 | subTasks 编排 | 设备裁决 | 分批 |
|------|--------------|---------|------|
| 潜在预警 0 | 关联分析 ×1 | deviceRequired=false | 单批 |
| 排查 1 | 扫描/连通 ×1 | 需匹配支持该技术处置方式的设备；不能自动匹配 → 人工选（保留 SafeSourceDriver） | 跨级联动按 AstUnitNum，否则单批 |
| 验证 2 | 单扫 / 交叉双扫（1026） | 需设备；交叉扫描两次须**不同厂家** | 同上 |
| 修复 3 | 修复登记 ×1 | deviceRequired=false（不绑定设备） | 跨级联动按 AstUnitNum，否则单批 |
| 核验 4 | 连通性检测 + 修复核验（Gate+Scan 波次） | 修复核验尽力按系统漏洞匹配历史扫描设备（已实现） | 跨级联动按 AstUnitNum，否则单批 |

**跨级联动横切规则（所有阶段生效）**：
- `AstUnitNum > 0` 时按其自动分批，**无手动 batchSize、无人工干预**；`= -1` 或 `<= 0` 不分批。
- 设备候选**强制限定 eng_hash_cnt 池**：`engDeviceMatcher.filterByAllowedHashes(devices, engHashCnt)`（现仅 verifyFixPlan 用，统一后排查/验证阶段也接入）。

### 2.3 单一裁决 `canConfirm`

每阶段的 `canConfirm` 只由该阶段自己的编排规则计算，杜绝"示意行卡死权威结论"：
- 阶段 0/3：无设备要求，`canConfirm=true`（其他校验通过时）。
- 阶段 1/2/4：`canConfirm = summary.allDevicesMatched && (非交叉 || dualVendor.ok)`。

## 五、兼容与灰度策略

- **接口过渡**：`dispatchPlan` 与旧双字段**并行返回一个迭代**。前端切到 `dispatchPlan` 并验证通过后，下个迭代删旧字段与旧组件。
- **confirmToken 不变**：阶段4 下发仍走 `requireConfirmToken`，token 由 verifyFixPlan 路径产生并挂到 `dispatchPlan.confirmToken`，下发协议零变更。
- **非核验阶段下发协议**：engHashes 来源从"SafeSourceDriver.onSubmit()"改为"从 dispatchPlan.subTasks 汇总"，须保证与人工勾选一致（排查/验证阶段人工选设备的场景不回归）。

## 六、验收标准

1. **核验阶段（4）+ 跨级联动 + AstUnitNum>0**：只显示一套预览；按 AstUnitNum 正确分批；设备匹配则确认按钮可点，不再永久置灰。
2. **核验阶段 + AstUnitNum=-1**：不分批，单批全量。
3. **排查/验证阶段（1/2）跨级联动**：设备候选仅限 eng_hash_cnt 池；池内无合法设备时红字提示且 canConfirm=false。
4. **验证阶段交叉扫描（1026）**：两次须不同厂家，否则 canConfirm=false。
5. **修复阶段（3）**：无设备要求，canConfirm=true。
6. **潜在预警（0）**：单条关联分析子任务。
7. **非跨级联动任务**：不再出现手动分批勾选；单批全量。
8. **零回归**：普通单设备（1022）/双厂家（1026）下发链路、confirmToken 校验、下发落库 engHashes 与整改前一致。
