## 1. 当前缺口：修复核验没接报告回调

创建任务子扫描走两条 Kafka：

| Topic                          | 作用          | 落库                           |
| ------------------------------ | ------------- | ------------------------------ |
| `task_finish_topic`            | 扫描完成      | `survey_id`、`status=FINISHED` |
| `download_report_finish_topic` | 报告/产物就绪 | `report_download_path`         |

修复核验目前只接了第一条，且用 `VFS-` 前缀单独分支；报告回调**被显式跳过**：

```36:38:project_backend/svmp/open-api-service/src/main/java/com/vtc/openapi/infra/adapter/taskcenter/TaskCenterReportRecycleService.java
        if (!StringUtils.hasText(openSubId) || openSubId.startsWith("VFS-")) {
            log.debug("task-center kafka report skipped extTaskId={}", event.getExtTaskId());
            return;
```

所以不是「不能复用」，而是**还没复用**，报告链路断了。

## 2. 为什么可以复用 `open_task_sub`

`open_task_sub` 本来就是 **VTC 子扫描的统一执行平面**，字段已够用：

- `sub_id` / `center_plan_id` / `survey_id` / `scanner_type` / `status` / `progress`
- `report_download_path`（报告产物）
- 下发约定：`extTaskId = OPEN-{subId}`

修复核验与创建任务在 VTC 侧是同一类 **SOC 漏洞扫描**，差异只在**业务后续**（ingest+验证 vs 指纹比对+6/7/10），不应再复制一张 sub 表。

现有编排已按 `scan_phase` 隔离：

| scan_phase             | 完成后的行为                    |
| ---------------------- | ------------------------------- |
| 1 排查                 | `captureOnSubFinished` → ingest |
| 2 验证                 | `tryAdvanceTask`                |
| **3 修复核验（新增）** | 指纹比对 → 跃迁 → Webhook       |

`captureOnSubFinished` 只处理 `PHASE_SURVEY`，不会误 ingest；`PHASE_VERIFY` 分支也不会误触发。

## 3. 修订方案：复用 `open_task_sub`，去掉 `job_sub`

### 3.1 数据分工

| 表                              | 职责                                            |
| ------------------------------- | ----------------------------------------------- |
| `open_verify_fix_job` / `_item` | Partner 业务面：受理、批次、case、逐实例 6/7/10 |
| **`open_task_sub`**             | VTC 执行面：下发、Kafka 回收、报告路径、轮询    |
| `open_task`                     | 锚定原排查任务（`task_id` 来自 item.taskId）    |

**不再新增** `open_verify_fix_job_sub`。

### 3.2 下发（按 scanner_type 分组）

```
verify-fix 受理
  → 选举：log.sub_id → open_task_sub.scanner_type
  → 按 (taskId, scanner_type) 分组   // 跨任务时再按 taskId 拆组
  → 每组创建 open_task_sub：
       sub_id      = SUB-xxx（与创建任务一致，不用 VFS-）
       task_id     = item.taskId（原 open_task）
       scan_phase  = 3（VERIFY_FIX，新增常量）
       scanner_type = 选举结果
       center_task_type = vuln
       verify_fix_job_id = jobId（可选扩展列，便于反查）
  → createSocScan(OPEN-SUB-xxx, ...)
  → job_item.rescan_sub_id = sub.sub_id
```

### 3.3 Kafka（与创建任务完全一致）

**`task_finish_topic`**

```text
onTaskFinish(event):
  sub = findBySubId(parseOpenSubId(event.extTaskId))
  if sub.scan_phase == 3:
      更新 survey_id / center_plan_id / FINISHED
      fetchAll(surveyId) → 本 sub 下 items 指纹比对
      若该 job 全部 phase=3 的 sub 完成 → 汇总 job → Webhook
  elif sub.scan_phase == 2: ...
  else: captureOnSubFinished(sub)  // 现有逻辑
```

**去掉** `VFS-` 特殊分支。

**`download_report_finish_topic`**

```text
onReportDownloadFinish(event):
  sub = findBySubId(...)   // 不再 skip VFS-
  sub.report_download_path = event.downloadPath
```

修复核验外发/下载报告产物时，与创建任务共用 `report_download_path` 和同一套外发组装逻辑（`exportStage=VERIFY_FIX_SCAN`）。

### 3.4 `open_task_sub` 最小扩展（可选但推荐）

```sql
ALTER open_task_sub ADD verify_fix_job_id VARCHAR(32);  -- 反查 job
-- scan_phase 注释扩展：3=修复核验复扫
```

`sub_id` 继续用 `SUB-` 前缀，**不必** `VFS-`。

## 4. 之前建议单独做 sub 表的原因 vs 复用

| 顾虑                      | 复用后的处理                                             |
| ------------------------- | -------------------------------------------------------- |
| 和 open_task 编排混在一起 | `scan_phase=3` 独立分支，不走 ingest/验证编排            |
| job 与 task 不是 1:1      | sub.`task_id` 锚原排查任务；`verify_fix_job_id` 指回 job |
| 一批跨多个 taskId         | 按 `(taskId, scanner_type)` 分组，多组 sub               |
| 报告回调                  | **复用后自动接通**，无需第二套消费者                     |

结论：**业务聚合留在 `open_verify_fix_job`，VTC 执行统一走 `open_task_sub`**，比双表更干净。

---

## 5. 更新后的端到端

```
Partner verify-fix
  → open_verify_fix_job + items
  → log → scanner_type → 按 (taskId, scanner_type) 写 open_task_sub(phase=3)
  → createSocScan（与创建任务相同）

Kafka task_finish_topic        → sub 完成 → phase=3 比对跃迁
Kafka download_report_finish   → sub.report_download_path（与创建任务相同）

全部 sub 完成 → job FINISHED → INSTANCE_VERIFY_FIX_COMPLETED
```

运营「待核验列表」：`job_item` JOIN `open_vuln_instance` JOIN `open_task_sub`（`rescan_sub_id`），默认 `taskId` 过滤。
