# 任务下发页面整改方案 v1.0

> 范围：`asset-newleak-manage` 前端「任务下发」抽屉（系统漏洞工单 / 跨级联动 / 产品预警共用）
> 目标：修复用户"选完设备仍报红、无法下发"的阻断问题，并按用户体验/产品设计优化信息架构。
> 原则：YAGNI、最小 diff、零功能回归；仅动前端展示与交互，不改后端契约与下发参数结构。

## 二、根因诊断（关键，先于所有 UI 优化）

### 🔴 P0-1 —「选了设备红色报错也不消除」是真实功能缺陷，非纯体验问题

- `PhaseDispatchPreview` 的红色报错来自后端返回的 `preview.message`（当 `preview.canConfirm === false`），其中 `deviceMatched === false` 渲染为「未匹配到合法设备」。
- 后端预览是否"匹配到设备"取决于请求里是否带 `engHashes`。预览请求在 `BaseInfo.getData()` 发出，`engHashes` 由 prop 传入。
- `BaseInfo` 的 `engHashes` 来自 `AddTaskDrawer` 的 `selectedEngHashes`；而 `selectedEngHashes` **只在 `onDualVendorChange`（1026 双厂家）里被赋值**。
- **普通 1022（混合）等单设备路径下，`SafeSourceDriver` 勾选设备后没有任何 `@change` 事件回传父级** → `selectedEngHashes` 恒为空 → 预览请求永不带 `engHashes` → 后端永远算作"未匹配" → 红色报错永不消除。

**结论**：截图中"设备都已注册、也能勾选，但预览一直红、`confirmDisabled` 恒 true"的现象，根因是 **SafeSourceDriver 选择结果未联动到预览**。这是本次整改的**头号必修项**。

> 注：下发时 `saveorSubmit()` 会二次调用 `this.$refs.SafeSourceDriver.onSubmit()` 拿到 `engHashes` 再提交，所以"最终下发"能带上设备；但因为 `confirmDisabled` 被预览的 `canConfirm===false` 卡住，用户根本点不到下发。形成死锁。

## 三、整改项清单（按优先级）

### 🔴 P0-1　SafeSourceDriver 选择联动预览（必修，解死锁）

**改动**：
1. `SafeSourceDriver.onSelectChange` 中新增 `this.$emit('change', this.selectedRows)`。
2. `AddTaskDrawer` 模板给 `<SafeSourceDriver>` 绑定 `@change="onSafeSourceChange"`。
3. `AddTaskDrawer` 新增方法：
   ```js
   onSafeSourceChange (rows) {
     this.selectedEngHashes = (rows || []).map(r => r.engHash).filter(Boolean)
   }
   ```
   复用已有的 `:engHashes="selectedEngHashes"` → `BaseInfo` watch → 重跑预览。

**效果**：勾选合法设备后，预览请求带上 `engHashes`，后端返回 `deviceMatched=true / canConfirm=true`，红色报错消除，`确认下发`自动可点。
**风险**：低。仅新增一条 emit 与一个赋值；1026 双厂家路径不受影响（走独立分支）；预警任务（`isShowSafeSourceDriver=false`）不渲染此组件。

---

### 🟠 P1-1　报错文案带动作指引 + 锚点跳转

**问题**：红色报错在预览区，设备选择在更下方，报错不告诉用户"去哪操作"。
**改动**（`PhaseDispatchPreview` 或 `AddTaskDrawer`）：
- 当 `canConfirm===false` 且原因是缺设备时，报错文案统一为：
  「尚未选择合法安全资源设备，请在下方"安全资源设备"中勾选后再确认下发」并附「定位到设备选择 ↓」链接，点击 `scrollIntoView` 到设备区并短暂高亮。
- 通过给设备区容器加 `ref` + `id`，`AddTaskDrawer` 提供 `scrollToDevice()`。

**风险**：低，纯展示与滚动。

---

### 🟠 P1-2　`确认下发`按钮 hover 原因提示

**问题**：`confirmDisabled` 为 true 时按钮灰但无说明。
**改动**：给按钮包一层 `a-tooltip`，`disabled` 时显示当前阻断原因（未选设备 / 双厂家未满足 / 预览未通过），可点时不显示。
**风险**：极低。

---

### 🟡 P1-3　基本信息分层：只读信息与操作项分离

**问题**：9 个只读字段与唯一操作项（技术处置方式/漏洞业务阶段下拉）混排，操作项被淹没。
**改动**（`BaseInfo` 模板，纯布局）：
- 只读字段（指令ID/工单类型/执行方式/任务名称/各类数量）归入「工单摘要」区；默认展示 4 项关键（指令ID、工单类型、执行方式、排查资产数量），其余「查看更多」折叠。
- `技术处置方式`、`漏洞业务阶段`两个 `a-select` 抽到独立「本次下发配置」区块，加浅色卡片背景 + 必填星号。
- **不改** `v-decorator` 字段名、校验规则、`changeprocMethod/changeTskPhase` 逻辑。

**风险**：中（改模板结构，需回归表单校验与预览触发）。**建议作为独立提交，与 P0/P1-1/P1-2 分开**。

---

### 🟡 P1-4　异常值 `-1` / 空值友好显示

**问题**：`封装资产数量单元` 显示 `-1`，暴露后端默认值。
**改动**：`BaseInfo` 对 `astUnitNum` 等做展示层兜底：`< 0 或 空` → 显示「—」并加 tooltip「暂无数据」。**不改**后端返回值与下发参数。
**风险**：低。

---

### 🟢 P2　视觉与一致性（可选，低优先）

- **色彩语义分级**：阻断用错误红，非阻断提醒（"1 项 未匹配"）用橙色，避免红色泛滥。（`PhaseDispatchPreview` warnings 已用 orange，基本符合，仅需核对。）
- **水印**：降低透明度/密度以免遮挡表格（属平台级组件，本次不改，仅记录）。
- **步骤指示**：抽屉内加「① 配置 → ② 选设备 → ③ 预览确认」引导条。改动偏大，本期不做，记入 backlog。

## 五、验收标准

1. 普通 1022 流程：勾选 ≥1 台已注册合法设备后，红色报错消除、`确认下发`变亮、可成功下发。（P0-1）
2. 未选设备时：报错文案含"去下方选择"指引，点击可定位到设备表；`确认下发`置灰且 hover 有原因。（P1-1/P1-2）
3. 1026 双厂家流程、产品预警流程、跨级切批流程行为与整改前一致（无回归）。
4. `-1` 等异常值显示为「—」。（P1-4）
5. 下发提交参数结构（`engHashes/procMethod/tskPhase/...`）与整改前完全一致。

## 六、不做/不碰清单（防扩散）

- 不改后端预览接口 `getVulnScanTaskPreDispatch` 契约与 `canConfirm/deviceMatched` 语义。
- 不改下发接口参数结构。
- 不动 `DualVendorScannerPick`、`VerifyFixPlanPreview` 的既有逻辑（除非 P0-1 联动必要）。
- 不改 `taskStatDict` 状态码映射。
- 不做全页化改造（抽屉→全页），维持 `a-drawer`。
