# M4 回退方案 · OperationCase 域迁回 open-api-service

> **版本**：v1.0  
> **日期**：2026-06-29  
> **性质**：回退 `00-主计划.md` 中 M4 里程碑，将 OperationCase 域从 platform-admin 迁回 open-api-service  
> **决策依据**：OperationCase 本质是业务执行面的聚合根，非控制面管理能力，不应迁入 platform-admin

---

## 0. 回退原因

### 0.1 原 M4 迁移决策回顾

M4 将 open-api-service 的 OperationCase 域（运营案件壳、工作台、多类型聚合）整体迁入 platform-admin，理由是：

> "platform-admin 定位为统一控制面/管理面，运营案件作为核心管理能力缺失"

### 0.2 该决策存在的问题

| 维度 | 分析 |
|------|------|
| **创建者** | case 由 open-api-service 的 InvocationPipeline 创建，platform-admin 永远不创建 case |
| **写入者** | case 状态由业务执行流程更新（异步任务完成 → case FINISHED），platform-admin 只读 |
| **聚合依赖** | 工作台需要 instance/task/verify-fix 域数据，这些域全部留在 open-api-service |
| **生命周期** | case 的生命周期与业务执行（mock → vul-pass）绑定，应随业务面一起迁移 |
| **本质属性** | OperationCase 是业务执行管道的产物，与 task、verify-fix、instance 同属「业务执行面」 |

### 0.3 结论

**OperationCase 的「读」和「写」都在业务执行面。把它迁到 platform-admin 等于把 aggregate root 从它的 bounded context 里撕裂出来。** 回退是最干净的方案。

## 2. 跨域关联方案

### 2.1 数据库层面

所有关联通过共享的 `open_api` 库自然实现：

```
open_operation_case.partner_id    ──→ partner 表（platform-admin 管理，但共享库可读）
open_operation_case.invocation_id ──→ api_invocation 表（platform-admin 管理，但共享库可读）
api_invocation.case_id            ──→ open_operation_case 表（open-api-service 管理）
webhook_delivery_log.case_id      ──→ open_operation_case 表（open-api-service 管理）
```

### 2.2 前端层面

**跨域关联 = 前端路由跳转**，不做后端耦合：

```
platform-admin 的调用记录列表
  │ invocation 行有一个 case_id 列
  │ 点击 case_id
  ▼
前端路由跳转到 open-api-service 的运营案件工作台
  /operation-cases/{caseId}
```

```
platform-admin 的 Webhook 投递记录列表
  │ delivery_log 行有一个 case_id 列
  │ 点击 case_id
  ▼
前端路由跳转到 open-api-service 的运营案件工作台
  /operation-cases/{caseId}
```

### 2.3 前端 API 路由

```
前端 → morningglory → open-api-service（业务执行面）
  ├── /internal/admin/operation-cases             列表查询
  ├── /internal/admin/operation-cases/{id}/workspace  完整工作台
  ├── /internal/admin/operation-cases/backfill       历史回填
  └── /internal/admin/operation-cases/{id}/actions/retry-dispatch  重试下发

前端 → morningglory → platform-admin（控制面）
  ├── /internal/admin/invocations                 调用记录（可展示 case_id 列）
  ├── /internal/admin/webhooks/delivery-logs      Webhook 投递（可展示 case_id 列）
  └── /internal/admin/partners                    合作伙伴管理
```

## 5. 后续演进路径

```
现在：open-api-service（mock 业务执行 + OperationCase）
                 │
        vul-pass 上线后
                 │
                 ▼
未来：vul-pass（真实业务执行 + OperationCase）
       open-api-service 逐步消亡或只保留 artifact/export
```

OperationCase 随业务执行面一起迁移，不需要任何「壳-肉分离」改造。

## 6. 风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| platform-admin 中其他模块引用了 OperationCase 的类 | 编译失败 | 删除前先 grep 全量引用，确认无跨模块依赖 |
| 前端 API 路由切换后 baseURL 配置不一致 | 接口 404 | 确认 morningglory 路由 + 前端 request 实例指向正确 |
| open-api-service 的 OperationCase 在迁移期间有改动 | 代码冲突 | 回退前对比两个版本，确认 open-api-service 侧为最新完整实现 |
| case_id 列在 platform-admin 的 Invocation/Webhook 视图中展示 | 前端需要跨域跳转 | 确认前端已有 case_id 列渲染为可点击链接 |
