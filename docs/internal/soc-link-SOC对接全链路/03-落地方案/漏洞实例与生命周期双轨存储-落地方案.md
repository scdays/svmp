## 一、背景与问题

### 1.1 平台定位

- **vul-pass** 作为平台**漏洞管理核心**：漏洞全生命周期（排查、验证、修复、核验修复）、资产覆盖、扫描管理，对标部侧建设指南。
- **扫描器对接**沿用 vul-pass 现有能力（`engHash`、安全资源设备等），**不强制**绑定 `vuln-task-center`（与历史 vuln-model 指标任务链路可并存演进）。
- **不新增独立微服务**（方案 C）：open-api-service 做 Partner 契约与治理，能力沉 vul-pass。

### 1.2 数据来源复杂

| 来源 | 说明 | 现状 |
|------|------|------|
| 部侧考核指令 | 工单驱动，`orderId` 强绑定 | vul-pass `VulScanTaskUi` 全流程 |
| vuln-model 指标任务 | 生产常态化排查 | 扫描在 model，结果导出 |
| 开放 API（Partner） | 外部排查/处置 | open-api-service P0/P1 |
| 本地工单 + XLSX 导入 | 每月常态化上报前的「洗数」 | `PlatformDefaultHandleXlsxParserV2` |

非考核入口产生的数据**来源不确定**；客户要求：**生产过程与部侧考核数据不能简单挂钩**，但部分生产数据需支撑**常态化 monthly 上报**。

### 1.3 现状痛点

1. **考核链**与**生产链**共用 `vul_scan_task*`、`vul_archive_inst`、`vul_inst_log_rela`，场景软隔离已设计（`tsk_scn`、`source` 等）**尚未启用**。
2. 生产排查在 **vuln-model** 完成，每月由运维 **导出 → vul-pass 建本地工单 → 导入漏洞 → 补台账 → 常态化上报**；链路手工、不可持续。
3. 部侧对系统漏洞查询依赖 **`vul_archive_inst` JOIN `vul_inst_log_rela`**，且上报要求 **`logIDLst`（台账）** 完整；生产真实轨迹往往**阶段不全、台账滞后**。
4. 上报生产数据时，往往需要 **补齐部侧要求的全生命周期阶段**（合规轨迹合成），与真实运维轨迹并存。

## 二、核心结论（Executive Summary）

| 决策项 | 结论 |
|--------|------|
| 实例主档 | **`vul_archive_inst` 全平台共用**，扩展 `data_origin` / `source` |
| 生命周期 | **`rela` 双轨**：运营轨（真实）+ 上报轨（部侧/合规） |
| 状态跃迁 | **只驱动 `inst`**，规则沿用现有 `transition`，不因双 rela 分裂 |
| 台账 | **运营轨可滞后**；**上报轨**在遴选后批量补 `log_ids` |
| 部侧查询 / 常态化 | **只读 `rela_report`**（+ inst JOIN） |
| open-api | 薄网关；实例映射 `vulInfoId`，写 vul-pass 内部 API |
| 演进 | 阶段 0 保留 Excel 导入；阶段 1+ pass 内常态化排查 + 遴选工作台 |

## 三、数据模型：一 inst + 双 rela

### 3.1 总体结构

```text
┌─────────────────────────────────────────────────────────────┐
│  vul_archive_inst（系统漏洞实例 · 共用主档）                    │
│  · 当前 vulInfoStat、资产/漏洞属性                             │
│  · data_origin：METRIC / OPEN / PROD / ASSESS / IMPORT         │
└───────────────────────────┬─────────────────────────────────┘
                            │ 1 : N
            ┌───────────────┴───────────────┐
            ▼                               ▼
┌───────────────────────┐       ┌───────────────────────┐
│  vul_inst_log_rela_oper │       │ vul_inst_log_rela_report │
│  （运营生命周期 · 真）   │       │ （上报生命周期 · 部侧面） │
│  · 每次真实状态变更追加  │       │ · 考核可实时写           │
│  · log_ids 可空/PENDING │       │ · 生产由遴选+合成批量写   │
│  · 不参与部侧默认查询    │       │ · log_ids 上报前必填     │
└───────────────────────┘       └───────────────────────┘
                                            │
                                            ▼
                              vuln_stats_upload / upload_list
                              （常态化批次快照）
```

> **命名说明**：现网表 `vul_inst_log_rela` 迁移时建议 **整体作为 `rela_report`**（历史多为导入上报）；新建 `vul_inst_log_rela_oper`。若历史更偏真实运维，则相反，以 DBA 盘点为准。

### 3.2 `vul_archive_inst`（共用）

**职责**：平台唯一「系统漏洞实例」；`transition`、资产匹配、开放 API 映射均指向此表。

**建议扩展字段**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `data_origin` | TINYINT/VARCHAR | METRIC / OPEN / PROD / ASSESS / IMPORT |
| `reportable_flag` | TINYINT | 0 永不报 / 1 可遴选 / 2 仅指令响应（可选） |

现有 `source`（0-部侧下发 / 1-企业发现）可保留，与 `data_origin` 正交。

### 3.3 `vul_inst_log_rela_oper`（运营轨）

**职责**：记录**真实**生命周期；多来源、只要有状态变更就追加。

| 字段 | 约束 | 说明 |
|------|------|------|
| `vul_info_id` | NOT NULL | → inst.id |
| `vul_info_stat` | NOT NULL | 该次变更后状态 |
| `transfer_time` | NOT NULL | 识别时间戳 |
| `tsk_id` | NOT NULL | 产生变更的任务/子任务 |
| `order_id` | **可空** | 生产/开放可无部侧指令 |
| `log_ids` | **可空** | 台账可后补；`ledger_status=PENDING` |
| `data_origin` | NOT NULL | 与 inst 一致 |
| `ledger_status` | NOT NULL | PENDING / FILLED / NA |
| `eng_hash`, `src_method`, `source` | 同现表 | |

**写入时机**：

- vul-pass 常态化排查任务状态变更  
- open-api 触发 verify / remediate / verify-fix（经 vul-pass Domain）  
- vuln-model 同步入 pass 后的变更  
- **不**在每次变更时写 report 轨

### 3.4 `vul_inst_log_rela_report`（上报轨）

**职责**：部侧**可读**生命周期；常态化、组合查询、测试数据接口 **JOIN 此表**。

在现 `vul_inst_log_rela` 字段基础上增加：

| 字段 | 说明 |
|------|------|
| `synthesized` | 0=真实同步（考核）/ 1=合规合成（生产上报） |
| `report_month` | 统计月，如 `2026-05` |
| `upload_batch_id` | 关联 `vuln_stats_upload.id` |
| `oper_rela_id` | 可选，指向 oper 轨来源行 |
| `ledger_status` | 上报前须 FILLED |

**写入时机**：

| 场景 | 行为 |
|------|------|
| 部侧考核指令 | 实时 append（`synthesized=0`，同步台账） |
| 生产遴选上报 | 批处理：按规则**合成全阶段** + 补 `log_ids` |
| 过渡：本地工单 XLSX 导入 | 可整包写 report（兼容现流程） |

### 3.5 第三层：常态化批次（已有）

- `vuln_stats_upload`：上报批次头  
- `vuln_stats_upload_list`：该次**实际上报**的实例快照  

从 **`rela_report`（已 FILLED + 已 SELECTED）** 生成 list，再走文件通道 / `VulnStatsUploadUI`。

## 四、业务流程

### 4.1 日常生产 / 开放 API（运营轨）

```text
排查/扫描 → 解析 → transition → 更新 vul_archive_inst
                              → append vul_inst_log_rela_oper
                              → （可选）不写台账 / 不回传部侧 order
```

与 `VulScanTaskUi` 的 recycle → handlerReport → handlerVulProcess **处理模式相同**，但：

- 走 **`biz_line=PROD|OPEN`** 编排入口（非 `/vul-scan-task/dispatch` 考核默认链）  
- `writeLedger` / `refreshOrderStatus` **跳过**或走 PROD 分支  
- **只写 oper 轨**，不写 report 轨

### 4.2 部侧考核（上报轨为主）

```text
dispatch(orderId) → … → handlerVulProcess
  → inst + rela_report（synthesized=0, log_ids 同步）
  → refreshOrderStatus
```

考核数据是否记 oper 轨：**可选**（建议记，留审计真相）。

### 4.3 每月常态化（运维收口）

```text
① 遴选（固定日期）
   从 rela_oper 筛选：report_month 内有关键动作（核验/修复等）的 vulInfoId
   交叉 inst 当前状态、reportable_flag

② 合成 report 轨（合规轨迹）
   对入选实例，按部侧阶段模板补全 rela_report 行
   synthesized=1；transfer_time 落在统计月内（规则可配置）
   缺阶段则「合成」——对应现网 Excel 导入的等价自动化

③ 补台账
   批量生成/关联 log_ids → ledger_status=FILLED
   校验 logIDLst 长度等（现 CommonUtil 校验逻辑）

④ 生成批次 & 上报
   vuln_stats_upload_list ← rela_report
   VulnStatsUploadUI / 文件通道 → 部侧
```

### 4.4 现状过渡（vuln-model 指标 → 导出 → 导入）

**阶段 0（保留）**：

```text
vuln-model 指标任务 → 导出 XLSX
  → vul-pass 本地工单 + recycle（PLATFORM_VUL_INST_XLSX_V2）
  → inst + rela_report（整包导入，等价手工合成）
  → 常态化上报
```

**阶段 1 目标**：model 结果**同步 inst + oper**，上报仍走 4.3 遴选合成，**逐步去掉**「每月整包 Excel 洗数」。

## 五、与 VulScanTaskUi 全流程的对应

| 阶段 | 参考接口 | 考核 | 生产/开放 |
|------|----------|------|-----------|
| 任务编排 | dispatch / preDispatch | orderId + 2FA + 台账任务 | PROD 任务，无部侧 order |
| 扫描执行 | （pass 内扫描器，非 task-center 必选） | 同左 | 同左 |
| 结果回收 | recycle / preview | 在线+离线 | 同左 |
| 标准化 | handlerReport | 同左 | 同左 |
| 生命周期 | submit / handlerVulProcess | inst + **report** + 台账 + 回传 | inst + **oper** only |
| 对外 | refreshOrderStatus | ? | ? |
| 常态化 | VulnStatsUpload | report 轨 | 遴选 → 合成 report → 上报 |

**跃迁规则（transition）**：仅依赖 **inst** + 原始结果，**不因双 rela 改代码路径**；rela 写入由编排层按 `biz_line` 分流。

## 六、方案 C 与 open-api 定位

### 6.1 架构

```text
Partner → partner-gateway → open-api-service
                              │ Feign /internal/open/**
                              ▼
                            vul-pass（漏洞管理核心）
                              ├── biz_line=OPEN|PROD|ASSESS
                              ├── inst + rela_oper / rela_report
                              └── 扫描器（engHash，非 vuln-task-center 必选）

部侧考核 UI/API ──────────────────→ vul-pass（biz_line=ASSESS）
vuln-model 指标 ──同步/导出────────→ vul-pass（data_origin=METRIC）
```

### 6.2 open-api 数据

- **`open_task` / `open_vuln_instance`**：Partner 索引与视图；**实体在 `vul_archive_inst`**。  
- **禁止**长期依赖 `POST /vul-scan-task/dispatch` + 假 `orderId` 作为引擎占位。  
- 实例读写：P1 经 Feign 映射 `vul-scan-task-sub-system` 或 internal open API；**部侧不可见 oper/report 区分**，Partner 只见平台 DTO。

## 七、部侧查询与 SQL 改造要点

现 `VulArchiveInstMapper.xml` 中 `getVulInfoWithLog`、`countByOrderId` 等均为：

```sql
FROM vul_archive_inst inst
INNER JOIN vul_inst_log_rela rela ON inst.id = rela.vul_info_id
```

**改造**：`vul_inst_log_rela` → **`vul_inst_log_rela_report`**，并视需要增加：

```sql
AND rela.ledger_status = 'FILLED'
AND rela.upload_batch_id IS NOT NULL  -- 或 report_month 条件
```

**运营侧**查询、Partner 内部排查：JOIN **`rela_oper`** 或只查 inst。

需梳理改造清单（非 exhaustive）：

- `VulArchiveInstMapper.xml` 全部 JOIN rela 的语句  
- `VulnStatsUploadListAppService` / 常态化明细  
- `TstDataInteractionDomainServiceImpl` 测试数据 tstType 5/6  
- `VulInstLogRelaUi.getVulLifecycleDetails`：建议分 oper/report 两个 API

## 八、阶段模板与合成规则（待产品确认）

部侧常态化常见状态链（参考 `VulStateEnum`）：

| 顺序 | 状态码 | 含义 | 合成策略（示例） |
|------|--------|------|------------------|
| 1 | 1 | 初始发现 | 无 oper 则合成；有则取 oper 最早发现 |
| 2 | 2/3 | 已验证有效/误报 | 来自 oper 或合成 |
| 3 | 5 | 已修复 | 来自 oper 或合成 |
| 4 | 6/7 | 核验修复/未修复 | 当月 oper 锚点 |

**合成器输入**：`vulInfoId`、`report_month`、`ctxCode`、oper 轨摘要、inst 当前 stat。  
**输出**：一批 `rela_report` 行（`synthesized=1`），待补 `log_ids`。

与现 **`PlatformDefaultHandleXlsxParserV2`** 校验规则对齐，避免合成后仍无法上报。

## 十、风险与对策

| 风险 | 对策 |
|------|------|
| inst 与 report 阶段不一致被抽查 | oper 永久保留；report 行标记 `synthesized`；保留 `oper_rela_id` |
| 双表维护成本 | 日常只写 oper；report 仅考核实时 + 每月批处理 |
| 历史 Mapper 漏改导致部侧查到 oper | 部侧 SQL 统一收口 report；Code Review 清单 |
| 合成规则与部侧口径漂移 | 阶段模板配置化；与 XLSX 导入校验共用规则模块 |
| open-api 与考核数据混写 | internal open API + `data_origin=OPEN`；禁止考核 dispatch 占位 |

## 十一、已否决 / 不推荐

| 方案 | 原因 |
|------|------|
| 生产/开放单独建 inst 表 | 跃迁规则双份；遴选映射痛苦 |
| 仅单表 rela + upload 标记 | 真实与合成混存，审计与运维理解成本高 |
| open-api 长期调考核 dispatch + 假 orderId | 不扫、污染考核域 |
| 为上报单独新建微服务 | 与「vul-pass 为核心、不增服务」冲突 |
